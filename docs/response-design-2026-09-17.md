**eBPF Trace — 탐지 이후의 대응 설계와 F1 개선 계획**

작성: 2026-09-17 · 상태: 구현 전 설계안 · 코드 기준: `fc57ea9`

후속 개발: PCAP 5일 준비·25개 피처·지도학습 비교는 [Context v2 검증](verification-2026-09-17-context.md)에 기록했습니다. 아래 F1 진단은 당시 목·금요일 실험 기준의 역사적 분석입니다. 사건 대응·알림 워크플로우는 계속 설계 단계입니다.

추천하는 다음 제품 목표는 **“탐지 이벤트를 담당자가 처리하고, 제한 조치의 효과와 복구까지 증명하는 사건 대응 워크스페이스”**다. 우선순위는 사건 묶음, 신뢰할 수 있는 Slack·이메일 전달, 담당자 확인, 승인형 기한부 대응이다. 탐지 모델 개선은 별도 실험으로 진행한다. 아래 시간과 정책은 제안값이며, 실제 서비스 수준이나 검증된 성능을 의미하지 않는다.

이 문서 작성 과정에서는 코드와 저장된 평가 데이터를 읽고 추가 진단을 수행했다. 외부 알림 전송, 차단, 운영 설정 변경, 새 모델 배포는 수행하지 않았다.

**현재 제품에서 출발해야 할 지점**

| 현재 확인한 구현 | 다음 단계에서 해결할 문제 |
|---|---|

| DB 저장 후 프로세스 내부 비동기 작업으로 전송 | 저장 직후 프로세스가 종료돼도 알림이 사라지지 않도록 보장 |
| 탐지 이벤트, 검토 의견, 시나리오 실행 결과 저장 | 누가 언제 판단·승인·조치했는지 연결된 이력 |
| 공유 관리자 토큰 | 실제 사용자 식별, 역할별 권한, 승인자의 책임 추적 |

| 9개 피처 실험 모델의 F1 62.92%, 운영은 rules-only | 피처 계약을 맞춘 독립 검증과 단계적 모델 배포 |

현재 VM 센서가 관측하는 인터페이스가 EC2 서비스의 실제 통신 경로에 있는지부터 등록해야 한다. VM의 인터페이스를 차단해도 그곳을 지나지 않는 EC2 트래픽에는 효과가 없다. 탐지 센서와 차단 위치를 동일하다고 가정하지 않는다.

**사용자가 경험할 하나의 완결된 흐름**

1. 이벤트가 발생하면 자산·서비스·공격 유형·방향·시간 간격을 기준으로 사건을 만들거나 기존 사건에 연결한다.
2. Slack 사건 카드에 대상 서비스, 근거, 서비스 영향, 담당자와 확인 기한을 표시한다. 반복 관측은 같은 사건의 수치와 스레드를 갱신한다.
3. 담당자가 `[확인하고 맡기]`를 누르면 대시보드와 Slack에 동일한 담당자가 표시된다. 단순 메시지 전송 성공과 사람이 사건을 인수한 상태를 구분한다.
4. `[대응 미리보기]`에서 대상, 적용 위치, 정상 이용자에 대한 예상 영향, 예외 대상, 종료 시간을 확인한다.
5. 권한 있는 사용자가 승인하면 제한된 범위의 대응을 실행한다. 실행 성공은 에이전트가 실제 정책 적용을 보고한 뒤 기록한다.
6. 유입량·차단량·정상 서비스 상태를 함께 비교한다. 기한이 끝나거나 서비스 상태가 악화되면 현장에서 정책을 해제하고 결과를 기록한다.
7. 종료 시 탐지 근거, 판단, 대응 전후 지표, 복구 여부와 다음 개선 항목을 요약한다.

예를 들어 동일 스캔에서 관측 창 1,000개가 생성돼도 담당자는 사건 카드 하나를 받는다. 이는 설계 예시이며 현재 측정값이 아니다. 스캔은 여러 목적지 포트를, DDoS는 여러 출발지를 하나의 사건에 포함할 수 있으므로 단순 5-tuple만으로 묶지 않는다. 모든 원본 이벤트 연결은 유지한다.

사건 상태는 `open → acknowledged → investigating → contained → recovering → resolved`로 관리한다. 오탐은 근거를 남기고 별도 종결할 수 있다. 대응이 적용됐다고 즉시 `contained`가 되는 것은 아니다. 효과를 확인해야 하며, 만료 후 공격이 계속되면 다시 조사 상태로 전환한다. 알림 실패와 대응 실패는 사건 상태와 별도의 상태로 기록한다.

**Slack·Gmail·추가 알림의 역할**

| 채널 | 권장 역할 | 사용자가 할 수 있는 동작 |
|---|---|---|
| Slack | 실시간 공동 대응과 담당자 인수 | 확인, 담당, 증거 보기, 대응 미리보기 |
| Gmail 등 이메일 | 긴급 알림의 보조 경로, 미확인 사건 안내, 종료 보고서와 정기 요약 | 로그인된 사건 상세 화면으로 이동 |
| 브라우저 알림 | 대시보드를 열어 둔 분석가의 주의 환기 | 사건 열기, 확인 |
| SMS·당직 도구 | 중요한 사건이 계속 미확인 상태일 때 추가 호출 | 당직자 호출, 사건 링크 |
| 대시보드 알림함 | 모든 채널의 처리 상태를 확인하는 기준 화면 | 전송 실패 원인 확인, 권한 있는 재시도 |

초기 라우팅 제안은 P1에 Slack·이메일 즉시 알림, 2분 미확인 시 차순위 담당자 호출, 5분 미확인 시 선택적으로 SMS를 사용하는 것이다. P2는 Slack에 사건별 알림을 보내고 이메일은 15분 요약, P3는 대시보드와 일일 요약에 포함한다. 우선순위는 자산 중요도, 서비스 장애, 반복성과 관측 근거를 조합한다. Isolation Forest 점수를 “공격 확률 93%”처럼 표시하지 않는다. 같은 피처를 사용하는 규칙과 모델의 동시 탐지를 독립된 두 증거로 세지 않는다.

Slack은 사건별 부모 메시지와 스레드를 유지하도록 Bot API 사용을 권장한다. 기존 incoming webhook도 Block Kit을 지원하지만, 장기간 메시지를 갱신하고 메시지 식별자를 관리하는 요구에는 Bot API가 편리하다. 카드에 비밀값이나 전체 패킷 내용을 넣지 않는다. [Slack webhook 공식 문서](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/)

Slack 동작 요청은 서명과 타임스탬프를 검증하고, 워크스페이스·사용자를 서비스 계정에 매핑한다. 처리 요청을 내구성 있게 접수한 후 3초 이내 응답하고 긴 작업은 워커가 처리한다. 사용자에게 보이는 “접수”와 “차단 완료”는 별개다. 재전송과 버튼 중복 클릭은 같은 요청으로 처리한다. [동작 처리](https://docs.slack.dev/interactivity/handling-user-interaction/), [요청 서명 검증](https://docs.slack.dev/authentication/verifying-requests-from-slack/)

Gmail 주소로 알림을 받기만 한다면 Gmail 계정 연동은 필요 없다. SMTP 또는 SES 같은 발송 서비스를 통해 전달할 수 있다. Google 계정을 발신자로 사용해야 할 때만 OAuth와 `gmail.send` 범위를 사용한다. 받은편지함 읽기 권한은 이 설계에 필요하지 않다. 이메일 링크의 GET 요청으로 차단·승인을 실행하지 않는다. 메일 보안 검사기가 링크를 먼저 열 수 있으므로 로그인 후 명시적 POST 동작으로 승인한다. [Gmail 전송 권한](https://developers.google.com/workspace/gmail/api/auth/scopes), [Gmail 발송 API](https://developers.google.com/workspace/gmail/api/guides/sending)

전송 기록에는 `queued`, `sending`, `provider_accepted`, `retrying`, `failed`, `unknown`을 남긴다. 제공자가 지원하는 경우 배달·반송 이벤트도 추가하되, 전송 접수·배달·사람의 확인을 구분한다. Slack의 429 응답은 `Retry-After`에 따라 처리한다. [Slack 제한](https://docs.slack.dev/apis/web-api/rate-limits/), [SES 알림](https://docs.aws.amazon.com/ses/latest/dg/monitor-sending-activity-using-notifications.html)

시뮬레이션은 기본적으로 외부 알림 없이 실행한다. 별도로 활성화한 테스트 채널에만 `[훈련]` 표시를 붙여 보낼 수 있도록 설계한다. 운영 당직 호출과 훈련 알림은 대상과 통계를 분리한다.

**제품을 차별화할 세 가지 대응 기능**

| 기능 | 구체적인 화면과 동작 | 필요한 근거 |
|---|---|---|
| 차단 영향 미리보기 | 적용 자산·서비스·방향, 관측된 정상 세션 영향, 보호 대상과 NAT 경고 표시 | 최근 흐름 요약, 자산 목록, 센서 위치, IP 출처 신뢰도 |
| 기한부 대응과 자동 해제 | `[승인 후 5분 제한]`, 남은 시간, 즉시 해제, 장애 시 해제 결과 표시 | 현장 에이전트, 로컬 만료, 정상 서비스 확인 지표 |
| 대응 성적표 | 탐지부터 인수·승인·적용·복구까지 타임라인과 전후 그래프 | 사건·알림·대응 ID 연결, 차단 전 유입량과 드롭 카운터 |

영향 미리보기는 관측된 범위의 추정치다. 현재 저장된 탐지 이벤트만으로 전체 정상 세션 영향을 정확히 계산할 수 없으므로, 제한된 보존 기간의 정상 흐름 요약을 추가해야 한다. 자료가 부족하면 “영향 불명”으로 표시하고 자동 대응을 금지한다.

대응 만료는 백엔드의 예약 작업에만 의존하지 않는다. 지원되는 방화벽의 timeout 또는 에이전트·커널 정책 만료를 사용해 백엔드와 연결이 끊겨도 기한이 지나면 정책이 해제되도록 한다. 최대 TTL을 서버와 에이전트 양쪽에서 검증한다. 관리 접속, DNS, 수집 경로 등 보호 대상을 제외하고, 서비스 오류율·지연 악화를 확인하면 자동 해제를 시도한다. 해제 실패는 별도 긴급 사건이다.

차단 후 탐지 이벤트가 줄었다고 공격이 끝났다고 결론 내리지 않는다. 센서가 차단 이후 지점에 있으면 단지 트래픽이 보이지 않을 수 있다. 차단 이전의 유입량, 정책 적중량, 정상 요청 성공률을 함께 보여 준다.

**공격별로 다른 대응을 적용한다**

| 관측 유형 | 먼저 확인할 증거 | 초기 대응안 | 적용 한계 |
|---|---|---|---|
| PortScan | 승인된 점검 여부, 반복성, 실제 출발지와 대상 포트 | 검증된 출발지·대상 서비스에 승인형 임시 제한 | NAT·공유 프록시 전체 차단 금지 |
| SYN Flood | 대상 서비스 집계, SYN/ACK·연결 완료, 정상 요청 상태 | 서비스별 연결률 제한, 짧은 TTL, 전후 비교 | 현재 XDP는 관측 전용이므로 별도 구현 필요 |
| 대역폭을 포화시키는 DDoS | 회선 사용량, 외부 가용성, 다수 출발지 | 상위 사업자·CDN·DDoS 완화 경로로 전환 요청 | 호스트에서 드롭해도 이미 포화된 상위 회선은 회복되지 않음 |
| LargeFlow | 백업·배포 일정, 전송 대상, 애플리케이션·엔드포인트 로그 | 추가 증거 확보, 승인 후 제한된 송신 경로 조치 | 많은 바이트만으로 정보 유출 확정 불가 |
| 로그인 무차별 대입 | 계정별 실패·성공·세션 로그 | 애플리케이션 어댑터로 추가 인증 또는 세션 무효화 | 현재 네트워크 피처만으로 계정 특정 불가 |
| SQLi·XSS | WAF·리버스 프록시·애플리케이션 로그 | 검증된 웹 정책 적용과 취약점 수정 연결 | 암호화된 L3/L4 관측만으로 페이로드 공격 판정 불가 |

AWS Security Group은 허용 규칙으로 작동하므로 개별 IP 거부 목록으로 설계하지 않는다. AWS WAF도 현재의 일반 EC2 인터페이스에 바로 붙는 방화벽이 아니다. HTTP(S) 서비스라면 ALB·CloudFront 등 지원되는 경로를 먼저 구성해야 한다. 회선 포화에는 상위 네트워크의 완화가 필요하다. [Security Group 규칙](https://docs.aws.amazon.com/vpc/latest/userguide/security-group-rules.html), [WAF 적용 대상](https://docs.aws.amazon.com/waf/latest/developerguide/web-acl.html), [CISA DDoS 대응 지침](https://www.cisa.gov/sites/default/files/2023-09/TLP%20CLEAR%20-DDOS%20Mitigations%20Guidance_508c.pdf)

| 알림 센터 | 채널별 전달 상태, 미확인 시간, 재시도 이력 | 사건 열기, 실패 재시도, 테스트 전송 |
| 네트워크 대시보드 | 관측 유입·차단·정상 성공률과 사건·조치 시점 표시 | 사건으로 이동, 적용 정책 보기 |
| 훈련 및 평가 | 훈련 실행 ID, 기대 탐지와 실제 결과, 인수·대응·복구 시간 | 미리보기 훈련, 허용된 실험실 검증, 결과 비교 |

상단 주요 지표는 미확인 중요 사건, 확인까지 걸린 시간, 검증된 대응까지 걸린 시간, 복구 실패 건수로 구성한다. 탐지 개수 자체를 대응 성과로 표현하지 않는다. 실제 관측, 합성 시나리오, 오프라인 PCAP 평가는 모든 화면과 그래프에 출처를 유지한다. PCAP의 과거 시각과 현재 수신 시각도 구분한다.

현재 합성 시나리오는 데이터베이스·탐지·UI 경로를 검증한다. 실제 패킷 수집과 차단을 검증하려면 소유한 격리 실험실에서 정상 클라이언트와 제한된 시험 트래픽을 함께 실행하는 별도 검증이 필요하다.

**백엔드·DB의 구체적인 변경안**

기존 PostgreSQL을 기준 저장소로 사용한다. 이벤트 저장, 사건 생성·갱신, 알림 outbox 생성을 한 트랜잭션으로 처리한다. 워커는 잠금과 임대를 사용해 작업을 가져가고 지수형 재시도·지터·최대 시도·실패 보관을 수행한다. 현재 Redis의 `allkeys-lru` 캐시 설정을 그대로 영속 작업 큐에 쓰지 않는다.

| 저장 구조 | 주요 내용 |
|---|---|
| `assets`, `enforcement_points` | 소유자·중요도·보호 대상, 센서·인터페이스·적용 가능한 조치 |
| `incidents`, `incident_events` | 사건 상태·우선순위·담당자·버전과 원본 이벤트 연결 |

| `action_requests`, `action_approvals`, `action_runs` | 미리보기, 승인 버전, 대상·TTL, 실행·해제 결과 |

사건 재개·갱신 알림의 중복 키는 사건 ID, 변경 버전, 알림 종류, 채널, 수신 대상으로 구성한다. 외부 제공자가 접수한 직후 응답이 끊기면 중복 전송 여부를 완전히 보장할 수 없으므로 `unknown` 상태를 남긴다. 내부 작업 중복 억제와 외부의 완전한 1회 전달을 혼동하지 않는다.

공유 토큰 대신 OIDC 등으로 사용자를 식별하고 열람자·분석가·대응자·관리자 권한을 분리한다. 중요 자산의 조치는 요청자와 승인자를 분리하는 정책을 지원한다. 웹 화면이나 Slack 입력이 임의의 root 명령이 되지 않도록 에이전트에는 허용된 조치 유형·대상·TTL만 전달한다. 에이전트는 인증된 연결, 짧은 작업 유효기간, 작업 ID, 정책 버전을 검증한다. 대상이 불명확하거나 에이전트 상태가 오래되면 신규 조치를 거부한다.

XDP ingress 차단과 송신 경로 격리는 다른 기능이다. 송신 제어는 해당 호스트의 방화벽·TC 등 별도 어댑터가 필요하다. Docker 서비스에는 호스트 방화벽 규칙이 실제 전달 경로에 적용되는지 실험실에서 확인해야 한다. 운영체제·어댑터별 자동 만료와 재부팅 동작도 검증한다.

보존 기간과 집계량은 디스크 사용량에 맞춰 정한다. 직전 배포 점검의 서버 잔여 공간은 약 668 MiB였으며 이 문서 작성 시점에 재측정하지 않았다. 사건·흐름 이력 확대 전 용량 재점검과 보존 정책을 먼저 적용한다. 동일 EC2 전체가 멈추면 그 안의 알림 워커도 멈추므로 가용성 경보는 외부의 독립된 모니터에서 받는다.

**F1 80%에 미달한 정확한 이유**

현재 수치는 9개 피처의 Isolation Forest를 보수적으로 정답 매칭한 평가 창에 적용한 결과다. 운영 규칙 탐지나 전체 제품의 정확도가 아니다. 80% 목표는 F1이며, “모든 공격의 80% 탐지”와도 다른 지표다.

| 지표 | 현재 값 |
|---|---:|
| 정밀도 Precision | 92.13% |
| 재현율 Recall | 47.78% |
| F1 | **62.92%** |
| 정상 창 오탐률 FPR | 4.11% |
| 탐지한 공격 창 / 놓친 공격 창 | 351,078 / **383,716** |
| DDoS 재현율 | 38.58% |
| PortScan 재현율 | 59.80% |
| 평가 창 수 | 1,464,136 |

정밀도보다 재현율이 문제다. 공격으로 분류한 창은 대부분 정답이지만, 공격으로 라벨된 창의 절반 이상을 정상으로 판단했다. 현재 정밀도를 그대로 유지한다고 가정하면 F1 80%에 필요한 재현율은 약 70.69%다. 정밀도와 재현율은 함께 변하므로 이 값은 산술적인 설명이다. [기존 평가](../ml/reports/evaluation/combined.json)

추가 진단에서 같은 모델의 점수 경계들을 비교했다. **현재 평가 표본에서 FPR 5% 이하를 유지하는 모든 임계값 중 최대 F1은 약 67.44%**였다. 따라서 이 모델과 표본에서는 임계값 조정만으로 기존 목표를 충족할 수 없다. 이미 확인한 평가 데이터를 재사용한 사후 진단으로, 새로운 검증 성능이나 배포 가능한 임계값 선정 결과가 아니다. [추가 진단 수치](response-ml-diagnostic-2026-09-17.json)

**직접 관측된 큰 문제는 트래픽 방향에 따른 편차다.** 동일 평가의 주소 방향별 재현율은 다음과 같다. 공식 데이터 설명에서 `192.168.10.50`은 피해 서버이고 `172.16.0.1`은 NAT 방화벽 주소다. 아래의 “피해 서버 방향”은 이 토폴로지를 근거로 붙인 해석이며, 원래 공격자의 공개 IP를 복원했다는 뜻은 아니다. [CIC-IDS2017 네트워크와 공격 설명](https://www.unb.ca/cic/datasets/ids-2017.html)

| 유형 | 평가 데이터에서 관측한 방향 | 공격 라벨 창 | 놓친 창 | 재현율 |
|---|---|---:|---:|---:|
| DDoS | 방화벽 → 피해 서버 | 179,013 | 169,728 | **5.19%** |
| DDoS | 피해 서버 → 방화벽 | 237,226 | 85,915 | 63.78% |
| PortScan | 방화벽 → 피해 서버 | 159,736 | 4,289 | **97.31%** |
| PortScan | 피해 서버 → 방화벽 | 158,819 | 123,784 | 22.06% |

PortScan의 들어오는 탐색은 잘 잡지만 응답 방향은 많이 놓친다. DDoS는 피해 서버로 들어오는 방향에서 특히 많이 놓친다. 이를 모두 “라벨 오류”라고 단정할 수는 없다. 양방향 플로우의 공격 라벨을 짧은 단방향 관측 창에 적용한 평가 의미와, 모델에 제공되는 정보가 다르다는 증거다. 반대 방향 창을 삭제해 점수를 올리기보다 양방향 정보를 결합하고 방향별 성능을 함께 평가해야 한다.

원인을 검증 수준에 따라 나누면 다음과 같다.

| 원인 | 확인된 사실 | 개선 방향 |
|---|---|---|
| 짧고 방향별로 나뉜 피처 | 놓친 DDoS·PortScan과 정상 창 모두 `pkt_rate` 중앙값이 1이다. 현재는 목적지 전체의 공격 집중도와 양방향 연결 상태가 부족하다. | 목적지 집계, 양방향 패킷·바이트 비율, 연결 완료율, SYN/ACK/RST와 여러 시간 길이의 집계 |
| 정상 이상치 탐지 모델의 한계 | 정상 3,384,391개 창으로만 학습한다. 공격 라벨은 학습 경계에 직접 사용하지 않는다. | 라벨을 사용하는 지도학습 후보와 IF를 같은 독립 검증에서 비교 |
| 아직 제한된 모델 설정 탐색 | 트리 100개, 트리당 표본 기본값 256, contamination 0.05다. 설정별 비교는 충분하지 않다. | 표본 수·모델 후보를 검증 집합에서 비교하되 지연·메모리도 측정 |
| 라벨과 평가 단위의 차이 | 매칭 커버리지는 82.12%이며, 양방향 플로우 라벨을 피처 창에 연결한다. | 방향·시간·프로토콜별 매칭 감사, 불명확한 행을 정상으로 채우지 않기 |
| 평가 범위 제한 | 현재 테스트의 공격 종류는 DDoS와 PortScan뿐이다. | 다른 공격·날짜·세션과 실제 정상 사용 패턴을 추가해 외부 검증 |

피처 부족이 유력한 개선 지점이지만, 각 피처가 F1을 얼마나 올릴지는 제거·추가 비교 실험으로 확인해야 한다. 트리당 기본 표본 수와 contamination의 의미는 scikit-learn 문서에서도 확인할 수 있다. contamination 5%는 목표 탐지율 또는 공격 비율 보장을 뜻하지 않는다. [Isolation Forest 문서](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.IsolationForest.html)

6개 피처에서 9개로 확장했을 때 같은 평가에서 F1은 50.14%에서 62.92%로 개선됐다. 다만 기존 실시간 피처 계약은 6개 기준이므로 실험 모델 파일만 교체해서는 안 된다. 수집·전처리·모델·API의 피처 이름, 순서, 단위, 결측 처리, 버전을 함께 맞춰야 한다.

매칭률 82.12%는 정답 라벨을 연결한 범위이며 정확도가 아니다. 또한 평가 표본의 공격 비율은 약 50.19%다. 예를 들어 실제 공격 비율이 1%이고 현재 재현율·오탐률이 그대로 유지된다고 가정하면 정밀도는 약 10.5%가 된다. 이는 운영 측정값이 아닌 기저율 효과의 산술 예시다. F1 80%와 FPR 5%를 통과하더라도 무조건 자동 차단할 근거가 되지는 않는다.

**80% 목표를 위한 실험 순서**

1. 기존 평가와 데이터 해시를 기준선으로 보존한다. 이번에 자세히 분석한 테스트는 이후 개선 과정에서 독립된 최종 시험으로 주장하지 않는다. 별도 날짜·세션을 잠가 새 최종 테스트로 준비한다.
2. 라벨을 방향·공격 종류·프로토콜·플로우 길이별로 감사한다. 매칭이 어려운 사례를 임의로 삭제하거나 정상으로 덮어쓰지 않고 제외 범위와 이유를 보고한다.
3. 첫 피처 실험은 피해 서비스의 전체 PPS·SYN률, 출발지 수, 양방향 비율과 연결 완료율을 추가한다. NAT로 원 출발지가 합쳐진 경우 출발지 수의 관측 한계도 표시한다. 1초·5초·30초 집계는 현재까지의 데이터만 사용한다.
4. IF 설정 변경, 규칙 기준선, 지도학습 후보를 비교한다. 우선 기존 scikit-learn 범위의 HistGradientBoosting 또는 RandomForest를 사용할 수 있다. 공격 클래스별 학습 예가 없는 경우의 성능은 별도의 미지 공격 평가로 구분한다. [지도학습 후보 문서](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.HistGradientBoostingClassifier.html)
5. 학습·임계값 보정·최종 시험을 나누고 날짜·공격 실행·양방향 플로우가 경계를 넘지 않게 한다. 집계 길이 이상의 시간 간격도 둔다. IP·정답 라벨·시나리오 식별자를 예측 피처로 넣지 않는다. 새 데이터에서 같은 공격을 여러 독립 세션으로 확보해야 이 분리가 가능하다. [교차 검증](https://scikit-learn.org/stable/modules/cross_validation.html), [임계값 조정](https://scikit-learn.org/stable/modules/classification_threshold.html)
6. 기존 창 단위 F1 ≥ 0.80, FPR ≤ 0.05를 계속 보고하면서 공격별 재현율, 방향별 재현율, 플로우·사건 단위 결과, 탐지 지연, 자산당 시간별 오탐 사건 수도 추가한다. 지표 단위를 바꿔 기존 목표를 통과한 것처럼 표시하지 않는다. 신뢰 구간은 상관된 창 대신 세션·날짜 단위 재표집으로 추정한다.
7. 새 모델은 shadow 모드에서 먼저 관측하고 규칙 결과와 비교한다. 피처 계약·정상 트래픽 영향·운영 비용을 통과한 뒤 승인형 대응에 연결한다. 좁은 범위의 자동 대응은 별도 검증을 거친다.

데이터 수집 기간, 새 공격 사례와 검증 결과를 보기 전에는 F1 80% 달성을 보장할 수 없다. 이미 분석한 표본에서 임계값만 낮추거나 행을 무작위 분할해 얻은 상승은 개선 근거로 삼지 않는다.

**사용자가 직접 준비하면 가장 도움이 되는 것**

| 우선순위 | 준비할 일 | 기대 효과 |
|---|---|---|
| 1 | 기존 목·금요일 외 월·화·수요일 원본 PCAP 확보; 이미 제공된 해당 요일의 TrafficLabelling 정답 파일과 연결 | 정상 사용과 공격 종류의 범위 확대 |
| 2 | 소유한 실험실에서 서로 다른 날짜에 정상 사용과 허용된 공격 시험을 반복하고 실행 기록 작성 | 별도 학습·보정·최종 시험 세션 확보 |
| 3 | 7~14일 정도의 실제 정상 흐름 요약 수집: 배포, 백업, 파일 전송, 승인된 점검 포함 | 실제 환경에서의 오탐 원인 파악 |
| 4 | 서버·서비스의 담당자, 중요도, 관리 IP, 승인된 스캐너·백업 일정 정리 | 올바른 우선순위와 안전한 대응 범위 |
| 5 | 미탐·오탐 사례를 근거와 함께 검토 | 잘못된 라벨과 부족한 피처를 구별 |
| 6 | 테스트용 Slack 채널, 이메일 수신·발신 방식, 대응 승인자, HTTPS 주소 결정 | 알림과 승인 흐름을 실제 환경에서 검증 |

월요일 데이터는 정상 트래픽만 포함하고 화·수요일에 추가 공격 유형이 포함된다. 해당 요일의 라벨은 이미 `label/TrafficLabelling /`에 있으므로 다시 제공할 필요가 없다. 원본 PCAP를 머신러닝용 숫자 CSV로 대체하면 동일한 피처 추출과 패킷·정답 정렬을 검증할 수 없다. [공식 데이터 구성](https://www.unb.ca/cic/datasets/ids-2017.html)

실험 기록에는 `scenario_id`, UTC 시작·종료, 관측 지점, 출발·대상 역할, 도구 버전, PCAP 해시, 실제 성공·실패와 정상 동작 여부를 남긴다. PCAP·센서·서버 시간을 동기화한다. 운영 수집은 승인된 범위에서 필요한 요약을 중심으로 보관하고, payload는 별도 필요성이 있을 때만 제한한다. 단순히 알림이 없었다는 이유로 정상 라벨을 붙이지 않는다.

검토 의견은 후보 라벨로 저장하고 재검증한 뒤 학습 데이터에 편입한다. 버튼 한 번으로 즉시 재학습·배포하지 않는다. GPU나 VM 사양 증설보다 먼저 데이터·피처·평가 분리를 개선하는 편이 현재 병목에 맞다.

**구현 순서와 완료 기준**

| 단계 | 개발 산출물 | 완료를 확인하는 기준 |
|---|---|---|
| P0: 사건과 전달 | HTTPS·사용자 권한, 자산 등록, 사건 DB, outbox 워커, Slack·이메일, 알림 센터 | 프로세스 재시작에도 작업 복구, 중복 이벤트 억제, 429·발송 실패 표시, 사람의 인수 추적 |
| P1: 승인형 대응 | 영향 미리보기, 대응 승인, 격리 실험실 에이전트, TTL·해제, 전후 그래프 | 승인 중복 실행 방지, 권한 검증, 보호 대상 제외, 백엔드 중단 중에도 현장 만료 |
| P2: 탐지 성능 개선 | 방향·목적지 피처, 새 데이터 분할, 후보 모델 비교, shadow 관측 | 새 최종 시험 보고서와 공격별 결과, 창 단위 목표 및 운영 오탐·지연 기준 평가 |
| P3: 제한된 자동화 | 충분히 검증된 서비스·정책에 한정한 자동 조치, 당직 호출, 종료 보고서 | 실제 효과·복구 검증, 정상 서비스 영향 한도와 자동화 중지 절차 검증 |

ML 실험은 P0·P1 개발과 독립적으로 진행할 수 있다. 사건·알림·승인 기능은 F1 목표 달성을 기다릴 필요가 없지만, 탐지 성능이 미달인 모델을 자동 차단의 근거로 승격하지 않는다.

수용 시험에는 실제 패킷 검증, 합성 시나리오, 중복 메시지, 알림 워커 중단, Slack 제한, 채널 장애, 승인 중복 클릭, 권한 부족, 오래된 에이전트, 정책 저장 공간 부족, 백엔드 단절, 정책 만료, 서비스 오류 증가를 포함한다. 테스트용 알림은 사전에 구성된 대상에서만 실행한다. 모든 시험에서 사건·알림·대응·복구 결과를 동일 실행 ID로 확인한다.

이 설계의 성공 기준은 탐지 건수 증가가 아니라 **중요 사건을 빠짐없이 담당자에게 전달하고, 근거 있는 대응과 정상 서비스 복구를 추적하는 것**이다. 준비·탐지·대응·복구와 지속적인 개선을 연결하는 방향은 NIST의 최신 사고 대응 지침과도 일치한다. [NIST SP 800-61 Rev. 3](https://www.nist.gov/publications/incident-response-recommendations-and-considerations-cybersecurity-risk-management-csf)
