> 이 보고서는 9월 15일 최초 조사 시점의 상태를 보존한다. 이후 사용자 지시로 디스크를 정리해 여유 약 1.6 GB를 확보했고, VM 기동 후 Collector 연결 및 새 트래픽 수신을 확인했다. 최신 상태와 후속 SSH 인증 성공 결과는 [tasks.md 후속 기록](tasks.md#다음-작업-재개-메모)을 따른다.

## 결론

핵심 수집·탐지·저장·대시보드 코드는 존재하며 로컬 Python 검사와 프론트 빌드는 통과한다. 그러나 현재 실시간 수집 경로는 정상으로 확인되지 않는다. EC2의 health 응답은 Collector 미연결을 나타내고 Ubuntu VM SSH는 시간 초과된다. EC2의 루트 디스크 여유는 608 MB이며 이전 자동 배포의 용량 부족 문제가 해결됐다는 근거가 없다.

다음 작업은 **VM 접근 및 수집 경로 복구, EC2 배포 용량 확보**다. CIC 원본·레이블 준비와 모델 검증 상태 강제도 ML 완료의 선행 조건이다. 현재 프로젝트를 최종 시연·릴리즈 가능한 상태로 판단할 수 없다. 현황과 작업 순서는 [tasks.md 재개 메모](tasks.md#다음-작업-재개-메모)에 반영한다.

## 커널 및 Collector

### 확인된 구현

`ebpf-agent/xdp_agent.c`는 Ethernet, 최대 2개 VLAN, IPv4, TCP/UDP를 파싱하며 모든 반환 경로에서 `XDP_PASS`를 사용한다. IPv4 fragmentation은 집계 대상에서 제외한다. 65,536개 LRU 플로우 맵, ring buffer, 설정 배열을 두며 TCP SYN 집계는 SYN이면서 ACK가 아닌 패킷을 센다. C/Python 이벤트 ABI는 112 bytes로 맞춘다.

`collector/reader.py`는 BPF link 파일 디스크립터로 attachment를 소유하고 종료 시 닫는다. `collector/main.py`는 ring 이벤트 외에도 매초 전체 맵을 읽어 짧은 플로우의 마지막 누적값을 반영한다. `collector/features.py`는 이전 snapshot과의 차분을 사용하고 1초 패킷/SYN 윈도우와 출발지별 10초 목적지 포트 분포를 계산한다.

Linux ring buffer는 공간 부족 시 예약에 실패할 수 있다. 현재 코드의 예약 실패 이후에도 커널 누적 카운터가 유지되고 주기적인 맵 조회가 있어 일부 이벤트 누락을 보완할 수 있지만, LRU에서 제거된 카운터까지 복원한다는 보장은 없다. 따라서 과거 제한된 패킷 테스트나 CPU 오버헤드 결과만으로 NF-P03의 전체 탐지 파이프라인 10,000 pps 무누락을 입증할 수 없다.[^1]

### 요구사항 차이

F-M03은 10초 내 동일 출발지의 20개 이상 목적지 포트 접근을 요구한다. 실제 `RuleEngine.detect()`는 목적지 포트 수와 엔트로피 임계값을 모두 충족해야 탐지한다. 균등한 20개 포트의 접근은 높은 엔트로피를 만들지만, 한 포트의 대량 정상 트래픽에 소수의 다른 포트 접근이 섞이면 포트 수만으로는 탐지가 보장되지 않는다. 요구사항을 유지하려면 포트 수 조건의 처리 및 테스트를 수정해야 하며, 엔트로피를 필수로 유지하려면 탐지 범위를 명시적으로 조정해야 한다.

F-D04는 Redis 3회 재시도 실패 후 관리자 알림을 요구한다. `SlidingWindowCache.add()`는 재시도 및 로그는 구현했으나 마지막에 `False`를 반환할 뿐 알림 경로는 없다. 장애 상태 전환당 알림을 한 번 보내고 복구 시 상태를 해제하는 방식 등을 검토할 수 있다. 이는 이후 구현 제안이며 현재 기능으로 간주하지 않는다.

Collector가 BPF reader를 직접 생성하는 구조이므로 eBPF attachment와 Collector 프로세스는 결합되어 있다. F-D05의 독립 재시작 요구와 실제 기대 동작을 구체화해야 한다. 이번에는 VM에 접속하지 못해 BPF cleanup·재연결·오버헤드를 다시 검증하지 않았다.

## ML 데이터와 모델 검증

### 데이터 준비의 실제 범위

CIC 공식 자료는 PCAP, 레이블이 있는 플로우 자료, ML용 CSV를 제공하며 CICFlowMeter로 추출한 80개 이상의 피처를 설명한다. 이것이 프로젝트의 1초/10초 윈도우 피처와 동일하다는 뜻은 아니다. 현재 `ml/preprocess.py`는 프로젝트의 6개 피처와 `Label`이 있는 CSV만 읽고, 원본 PCAP replay나 시간·5-tuple 레이블 join을 수행하지 않는다.[^2]

다음 데이터 처리 단계가 필요하다.

1. 정상 및 공격 PCAP/레이블 파일 목록과 출처, 파일 무결성을 기록한다.
2. 캡처 시각·시간대·flow 방향·TCP SYN 판정·바이트 계산 범위를 고정한다.
3. 실시간 Collector와 같은 윈도우 및 집계 규칙으로 피처를 만든다. 패킷별 계산만으로는 현재 snapshot 반영 주기까지 자동으로 같아지지 않으므로 parity 검증이 필요하다.
4. 시간/5-tuple 레이블을 결합하고 미매칭·중복·혼합 레이블 윈도우의 처리 기준과 수를 기록한다.
5. 동일 출발지의 겹치는 10초 윈도우가 학습·평가 양쪽으로 새지 않도록 캡처/시간 구간 단위 분리와 경계 구간 처리를 설계한다.

### 학습 코드의 장점과 보완점

현재 전처리는 분할 후 정상 학습 행에만 StandardScaler를 적합하고 IsolationForest도 정상 학습 행에만 적합한다. 이는 전체 데이터에 스케일러를 먼저 적합하는 전처리 누수를 방지한다. 다만 행 단위 무작위 분리만으로 시간적으로 겹친 피처의 독립성이 확보되는 것은 아니므로, 위의 시간/그룹 분리 정책은 별도로 필요하다. 이 판단은 현재 피처 윈도우 구조와 공식 데이터 누수 예방 원칙을 결합한 분석이다.[^3]

IsolationForest의 `contamination=0.05`는 학습 점수의 판단 경계 설정에 쓰이며 실제 독립 평가 데이터의 FPR 5%를 보장하지 않는다. 기본 운영 임계값 -0.1에서는 `clip(decision_function - 0.1, -1, 0) < -0.1`과 검증 코드의 `decision_function < 0`이 대응한다. 관리자가 런타임 anomaly threshold를 변경하면 이 기본 임계값 검증 결과를 그대로 새로운 설정의 성능으로 사용할 수 없다.[^4]

`ml.validate`는 F1 ≥ 0.80, FPR ≤ 0.05 통과 여부를 기록하고 실패 시 CLI에서 exit 1을 반환한다. 그러나 `DetectionEngine`은 모델/스케일러 파일만 읽고 `model_version.json`의 `validated`를 확인하지 않는다. 현재의 “검증된 모델만 운영 반영”은 자동으로 강제되는 보장이 아니다. 모델/스케일러의 세트 일치, 피처 이름·순서, 라이브러리 버전, 검증 결과 및 임계값을 포함한 배포 검증이 필요하다.

이번에 설치된 scikit-learn은 1.9.1이며 열람한 stable 문서도 1.9.1이다. 과거 서버 이미지의 패키지 버전은 조회하지 않았다. 현재 `requirements.txt`의 범위 지정만으로 학습/운영 버전이 항상 일치한다고 볼 수 없다.

## 백엔드·대시보드·알림

### 저장 및 재전송

Collector는 SQLite outbox에서 ACK를 받은 메시지만 삭제한다. 백엔드는 탐지 이벤트를 commit한 후 dashboard broadcast 및 ACK를 수행하며 `message_id`로 이미 저장된 이벤트를 조회한다. DB 오류 때 연결을 닫아 미확인 메시지를 재전송하게 하는 흐름이 구현되어 있다. 로컬 테스트는 ACK 유실 후 replay 및 API 저장 흐름을 포함한다.

이 방식이 모든 장애에서 exactly-once 처리를 보장한다고 확대하면 안 된다. 탐지 판정이 재전송 전에 다시 수행되고, 정상 피처는 탐지 이벤트 테이블에 저장되지 않는다. 운영 임계값이 바뀌거나 여러 Collector 연결에서 같은 메시지가 동시에 들어오는 상황은 별도 범위의 검증이 필요하다.

### UI 확인 범위

Zustand 스토어는 이벤트 ID 중복 제거, 최근 300개 시계열 bucket, null ML 점수를 지원한다. WebSocket 훅은 지수 백오프와 최대 5회 재접속을 구현한다. 이번 TypeScript/Vite 빌드는 통과했지만 실제 브라우저의 화면, 모바일 레이아웃, 재접속 후 이력 복원 및 표시 지연은 재검증하지 않았다. JS 청크 675.03 kB의 경고는 기능 실패는 아니며 초기 로딩 최적화 검토 항목이다.

### Slack

`backend/services/alert.py`는 Critical 이벤트만 전송하며 HTTPX/httpcore URL 로그 레벨을 올리고 예외의 타입만 기록한다. Slack 공식 문서는 일반적인 발송 성공을 HTTP 200과 본문 `ok`로 설명한다. 현재 구현은 `raise_for_status()`와 본문 확인을 사용하지만 이번에는 실제 메시지를 전송하지 않았다. API 성공과 실제 채널 표시·1분 내 도착 여부는 각각 기록해야 한다.[^5]

9월 11일 기록은 Webhook 저장과 신규 코드의 배포 실패를 구분한다. 이번에 확인한 것은 기존 dev 이미지가 실행된다는 사실이며, 해당 이미지 내부 알림 코드나 실제 Webhook 활성 여부는 재확인하지 않았다.

## 배포 용량과 Terraform

### 디스크 부족의 의미

CI/CD는 VM runner에서 검사한 소스를 EC2에 업로드하고, EC2에서 Compose build → push → deploy를 실행한다. 기존 실패는 backend 이미지 export/unpack 단계의 `no space left on device`였다. 현재는 당시 마지막 여유 775 MB보다 적은 608 MB가 남아 있다. 실패 원인 코드나 저장 공간이 개선됐다는 근거가 없으므로 단순 재실행은 성공 가능성을 입증하지 못한다.

Docker는 registry exporter로 빌드 결과를 직접 push할 수 있다. 이를 별도 builder 또는 빌드 호스트 분리와 조합하면 운영 호스트의 빌드 산출물 저장 부담을 줄일 수 있다. 그러나 build cache와 배포 시 image pull/unpack 공간은 여전히 필요하므로 direct push만으로 608 MB 문제가 해결된다고 단정해서는 안 된다.[^6]

권장 검토 순서는 실제 용량/사용 주체 조회 → 기존 볼륨 보존 계획 → EBS 또는 빌드 위치 결정 → 빌드 전 여유 공간 검사 → 대상 SHA 배포 및 health 검증이다. EBS 크기를 늘리는 경우 볼륨뿐 아니라 파티션과 파일시스템의 확장 필요 여부도 확인해야 한다. AWS는 파일시스템 종류에 따라 절차가 다름을 명시하므로 실제 장치를 확인하기 전 고정 장치명의 확장 명령을 실행해서는 안 된다.[^7]

### 기존 자원 재사용

`infra/main.tf`는 Ubuntu 22.04 최신 AMI와 20 GB 루트 볼륨을 가진 신규 VPC/EC2를 정의한다. 과거 검증의 실제 EC2는 Ubuntu 24.04이고 이번 파일시스템 크기도 6.8 GB다. 따라서 현재 Terraform 정의가 실제 운영 자원을 이미 관리한다고 해석할 수 없다.

Terraform import는 기존 자원을 state에 연결하는 방법이다. 운영 환경에 맞는 자원 ID·AMI·네트워크·볼륨 값을 확보하고 무교체 plan을 확인하는 과정이 필요하다. `prevent_destroy=true`만으로 신규 자원 생성이나 모든 변경을 방지할 수 있다고 가정하지 않는다. EC2 조회 권한 부족과 OIDC/S3 state 미완료는 9월 11일 기록이며 현재 권한 상태는 재확인 대상이다.[^8]

## 후속 작업 우선순위

1. **수집 경로:** VM 전원·IP·네트워크·SSH 확인 후 Collector/터널/runner 상태를 조회한다. 연결 복구 후 새 피처가 수신되는지 확인한다.
2. **배포 복구:** EC2 용량 계획을 확정하고 용량 선행 검사를 추가한 뒤 CI/CD를 검증한다. 운영 이미지의 SHA와 DB 보존을 확인한다.
3. **실데이터 ML:** PCAP·레이블을 준비하고 변환/분리/학습/검증 경로를 완성한다. 통과 메타데이터와 산출물 일치를 로더에서 확인한다.
4. **요구사항 보완:** Redis 장애 알림, Port Scan 판정 기준, Collector 독립성, 실제 DB/Redis CI 검증 범위를 정리한다.
5. **최종 검증:** 기존 자원의 IaC 편입, SG 실측, 사용자 경로 성능, 격리망 시연, 명시적으로 지시된 Slack 발송 검증을 마친 후 문서 완료 상태와 릴리즈를 정한다.

이번 변경은 조사·진행·검증 문서와 README의 상태 정리에 한정한다. 기존 작업 체크 상태를 일괄 완료로 바꾸지 않으며, 서버 접근 문제와 보충 조건이 해결되기 전 다음 구현·배포 task는 보류한다.
