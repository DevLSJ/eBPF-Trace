# eBPF 기반 이상 트래픽 탐지 및 대응 시스템 — 요구사항 명세서

> 작성 기준일: 2026-09-09  
> 작성 원칙: SMART (Specific / Measurable / Achievable / Relevant / Time-bound)  
> 우선순위: 🔴 Must-have / 🟡 Should-have / 🔵 Could-have

---

## 1. 개요

본 문서는 eBPF/XDP 기반 커널 수준 패킷 수집, ML 기반 이상 탐지, 실시간 대시보드 시각화,
클라우드 배포(AWS EC2 + Terraform)를 포함한 시스템의 기능 및 비기능 요구사항을 정의한다.

---

## 2. 이해관계자 및 사용자 정의

| 사용자 유형 | 설명 |
|---|---|
| 네트워크 관리자 | 실시간 트래픽 현황 및 이상 탐지 이벤트를 모니터링하는 주 사용자 |
| 시스템 운영자 | 대응 규칙 설정, 시스템 상태 확인, 알림 수신을 담당 |
| 개발자 | eBPF 에이전트 및 백엔드 API를 개발·유지보수 |

## 3. 기능 요구사항

### 3-1. 커널 수준 패킷 수집

| ID | 요구사항 | 우선순위 | 측정 기준 |
|---|---|---|---|
| F-K01 | 사용자가 시스템을 시작하면 eBPF/XDP 에이전트가 지정 네트워크 인터페이스에서 패킷 수집을 1초 이내에 시작할 수 있어야 한다 | 🔴 Must | 에이전트 시작 후 첫 이벤트 수신까지 ≤ 1초 |
| F-K02 | 시스템은 플로우(src_ip, dst_ip, src_port, dst_port, protocol) 단위로 패킷 수/바이트 수를 BPF_HASH 맵에서 커널 내 1차 집계할 수 있어야 한다 | 🔴 Must | 플로우별 집계 정확도 100% (단위 테스트 기준) |
| F-K03 | eBPF 에이전트는 XDP native 모드로 동작하여 패킷 복사 없이 관찰할 수 있어야 한다 | 🔴 Must | CPU 오버헤드 eBPF 미적용 대비 5% 이내 증가 |
| F-K04 | 에이전트가 비정상 종료될 경우 커널 BPF 맵이 자동으로 해제되어야 한다 | 🔴 Must | 프로세스 종료 후 `/sys/fs/bpf` 잔여 맵 없음 확인 |
| F-K05 | 사용자는 bpftrace를 통해 개발 중 실시간 디버깅 정보를 조회할 수 있어야 한다 | 🔵 Could | bpftrace 스크립트 실행 및 출력 확인 가능 |

### 3-2. 데이터 수집 API

| ID | 요구사항 | 우선순위 | 측정 기준 |
|---|---|---|---|
| F-D01 | 시스템은 ring_buffer에서 커널 이벤트를 읽어 플로우 단위 피처(패킷 수, 바이트 수, 플로우 지속 시간, 프로토콜)로 집계할 수 있어야 한다 | 🔴 Must | 1초 슬라이딩 윈도우 기준 피처 계산 정확도 검증 |
| F-D02 | 집계된 피처는 Redis 슬라이딩 윈도우 캐시에 저장되어 최근 60초 데이터를 유지할 수 있어야 한다 | 🔴 Must | Redis TTL 설정 60초, 만료 후 자동 삭제 확인 |
| F-D03 | 수집 API는 WebSocket을 통해 백엔드로 실시간 이벤트를 스트리밍할 수 있어야 한다 | 🔴 Must | 이벤트 발생 후 백엔드 수신까지 지연 ≤ 500ms |
| F-D04 | Redis 연결이 끊어진 경우 수집 API는 오류 로그를 남기고 재연결을 3회 시도한 후 관리자에게 알림을 발송해야 한다 | 🟡 Should | 재연결 시도 로그 및 Slack 알림 수신 확인 |
| F-D05 | 수집 API는 eBPF 에이전트와 독립적으로 재시작 가능해야 한다 | 🟡 Should | 에이전트 재시작 시 API 서비스 무중단 유지 |

### 3-3. ML 분석 엔진

| ID | 요구사항 | 우선순위 | 측정 기준 |
|---|---|---|---|
| F-M01 | 시스템은 Isolation Forest 모델을 사용하여 비지도 방식으로 이상 트래픽을 탐지할 수 있어야 한다 | 🔴 Must | CIC-IDS-2017 데이터셋 기준 F1-Score ≥ 0.80 |
| F-M02 | 시스템은 Rule-based 방식으로 SYN Flood(임계값: 초당 SYN 패킷 1,000개 이상)를 즉각 탐지할 수 있어야 한다 | 🔴 Must | hping3 시연 시 탐지까지 ≤ 3초 |
| F-M03 | 시스템은 Rule-based 방식으로 Port Scan(임계값: 10초 내 동일 src_ip에서 20개 이상 포트 접근)을 탐지할 수 있어야 한다 | 🔴 Must | nmap 시연 시 탐지까지 ≤ 5초 |
| F-M04 | 탐지된 이상 트래픽은 심각도(Critical / High / Medium / Low)로 분류되어 백엔드에 전달되어야 한다 | 🔴 Must | 심각도 분류 결과가 PostgreSQL 로그에 저장됨 확인 |
| F-M05 | FPR(False Positive Rate)은 5% 이하를 유지해야 한다 | 🔴 Must | CIC-IDS-2017 검증 결과 FPR ≤ 0.05 |
| F-M06 | 모델은 신규 정상 트래픽 패턴에 대해 재학습 없이 점진적으로 적응할 수 있어야 한다 | 🔵 Could | 재학습 없이 2주 경과 후 FPR 유지 여부 확인 |

### 3-4. 백엔드 (FastAPI — AWS EC2)

| ID | 요구사항 | 우선순위 | 측정 기준 |
|---|---|---|---|
| F-B01 | 사용자는 REST API를 통해 이상 탐지 이벤트 목록을 페이지네이션으로 조회할 수 있어야 한다 | 🔴 Must | GET /api/events 응답 시간 ≤ 200ms (100건 기준) |
| F-B02 | 백엔드는 WebSocket 연결을 통해 실시간 이상 탐지 이벤트를 프론트엔드로 푸시할 수 있어야 한다 | 🔴 Must | 이벤트 탐지 후 프론트엔드 수신까지 ≤ 1초 |
| F-B03 | 모든 이상 탐지 이벤트는 탐지 시각, 플로우 정보, 심각도, 이상 점수와 함께 PostgreSQL에 저장되어야 한다 | 🔴 Must | 이벤트 누락 없이 DB 저장 확인 (100% 저장율) |
| F-B04 | 백엔드는 psutil을 통해 CPU/메모리 사용률을 10초 간격으로 수집하여 제공해야 한다 | 🟡 Should | GET /api/metrics 응답에 CPU/메모리 수치 포함 확인 |
| F-B05 | Critical 이상 탐지 이벤트 발생 시 Slack Webhook으로 알림을 1분 이내에 발송해야 한다 | 🟡 Should | Slack 채널에서 알림 수신 시간 확인 |
| F-B06 | 백엔드 API는 잘못된 요청(400)과 서버 오류(500)에 대해 표준화된 JSON 에러 응답을 반환해야 한다 | 🟡 Should | 각 오류 케이스별 응답 포맷 일관성 확인 |
| F-B07 | 사용자는 API를 통해 Rule-based 탐지 임계값을 런타임에 수정할 수 있어야 한다 | 🔵 Could | 임계값 변경 후 즉시 탐지 기준에 반영됨 확인 |

### 3-5. 프론트엔드 (Vite + TypeScript + React)

| ID | 요구사항 | 우선순위 | 측정 기준 |
|---|---|---|---|
| F-F01 | 사용자는 단일 대시보드에서 실시간 트래픽 현황, 이상 탐지 이벤트, 시스템 메트릭을 동시에 확인할 수 있어야 한다 | 🔴 Must | 3개 영역이 단일 화면에 표시됨 확인 |
| F-F02 | 사용자는 Recharts 기반 시계열 차트에서 최근 5분간 트래픽 추이와 이상 점수를 확인할 수 있어야 한다 | 🔴 Must | 차트 데이터 갱신 주기 ≤ 1초 |
| F-F03 | 이상 탐지 이벤트 발생 시 대시보드에 심각도별 색상(Critical: 빨강 / High: 주황 / Medium: 노랑 / Low: 파랑)으로 즉시 표시되어야 한다 | 🔴 Must | 이벤트 수신 후 UI 반영까지 ≤ 1초 |
| F-F04 | WebSocket 연결이 끊어진 경우 사용자에게 "연결 끊김" 상태를 UI에서 명확히 표시하고 자동 재연결을 시도해야 한다 | 🔴 Must | 연결 끊김 후 3초 이내 UI 상태 표시 및 재연결 시도 확인 |
| F-F05 | 사용자는 이상 탐지 이벤트 목록을 심각도 및 시간 기준으로 필터링할 수 있어야 한다 | 🟡 Should | 필터 적용 후 결과 반영 ≤ 500ms |
| F-F06 | 대시보드는 모바일 환경(768px 이하)에서도 주요 정보가 깨지지 않고 표시되어야 한다 | 🔵 Could | 모바일 뷰포트 기준 레이아웃 이상 없음 확인 |

## 4. 비기능 요구사항

### 4-1. 성능

| ID | 요구사항 | 우선순위 | 측정 기준 |
|---|---|---|---|
| NF-P01 | eBPF 에이전트 실행 시 호스트 CPU 오버헤드는 미적용 대비 5% 이내여야 한다 | 🔴 Must | psutil로 eBPF 적용 전후 CPU 사용률 비교 측정 |
| NF-P02 | 백엔드 API 평균 응답 시간은 200ms 이하여야 한다 | 🔴 Must | 부하 테스트(동시 접속 10명) 기준 P95 ≤ 200ms |
| NF-P03 | 시스템은 초당 10,000 패킷 이상의 트래픽에서도 이상 탐지를 수행할 수 있어야 한다 | 🟡 Should | hping3 고부하 시나리오에서 탐지 누락 없음 확인 |

### 4-2. 신뢰성

| ID | 요구사항 | 우선순위 | 측정 기준 |
|---|---|---|---|
| NF-R01 | 백엔드 서비스가 비정상 종료된 경우 Docker Compose restart 정책에 의해 60초 이내 자동 재시작되어야 한다 | 🔴 Must | `restart: unless-stopped` 정책 적용 및 재시작 확인 |
| NF-R02 | PostgreSQL 데이터는 Docker 볼륨으로 영속화되어 컨테이너 재시작 후에도 유지되어야 한다 | 🔴 Must | 컨테이너 재시작 후 데이터 유실 없음 확인 |
| NF-R03 | Redis 장애 시 이상 탐지 Rule-based 기능은 캐시 없이도 동작해야 한다 | 🟡 Should | Redis 중단 상태에서 Rule-based 탐지 동작 확인 |

### 4-3. 보안

| ID | 요구사항 | 우선순위 | 측정 기준 |
|---|---|---|---|
| NF-S01 | eBPF 에이전트 컨테이너는 CAP_BPF + CAP_NET_ADMIN 최소 권한만 부여하고, 불필요한 privileged 권한을 제거해야 한다 | 🟡 Should | Docker inspect로 capabilities 확인 |
| NF-S02 | EC2 Security Group은 웹(80, 443)과 관리자 IP의 SSH(22)만 허용하며 8000, 5432, 6379는 외부에 개방하지 않아야 한다 | 🔴 Must | Terraform 코드 및 AWS 콘솔에서 SG 규칙 확인 |
| NF-S03 | PostgreSQL은 외부 접근을 차단하고 Docker 내부 네트워크에서만 접근 가능해야 한다 | 🔴 Must | 외부에서 5432 포트 접근 불가 확인 |
| NF-S04 | Slack Webhook URL 등 민감 정보는 환경 변수(.env)로 관리하고 Git에 커밋되어서는 안 된다 | 🔴 Must | `.gitignore`에 `.env` 포함 여부 및 Git 히스토리 확인 |

### 4-4. 유지보수성

| ID | 요구사항 | 우선순위 | 측정 기준 |
|---|---|---|---|
| NF-M01 | 모든 서비스는 Docker Compose로 단일 명령(`docker compose up -d`)으로 실행 가능해야 한다 | 🔴 Must | 초기 환경에서 명령 1회 실행 후 전체 서비스 정상 기동 확인 |
| NF-M02 | EC2 인프라는 Terraform으로 코드화되어 `terraform apply` 1회로 환경을 재현할 수 있어야 한다 | 🔴 Must | 신규 AWS 계정에서 Terraform 적용 후 동일 환경 재현 확인 |
| NF-M03 | GitHub Actions에서 main 브랜치 푸시 시 Docker 이미지를 자동 빌드하고 EC2에 배포해야 한다 | 🟡 Should | 푸시 후 15분 이내 EC2 서비스 업데이트 확인 |

## 5. 인프라 요구사항

| ID | 요구사항 | 우선순위 | 측정 기준 |
|---|---|---|---|
| NF-I01 | eBPF 에이전트는 커널 5.15 이상의 Linux VM에서 실행되어야 한다 | 🔴 Must | `uname -r` 버전 확인 |

| NF-I04 | 시연 시 공격 트래픽(hping3, nmap)은 동일 VPC 내 별도 인스턴스 또는 로컬 VM에서만 발생시켜야 한다 | 🔴 Must | AWS 이용약관 준수 (외부 공인 IP 대상 공격성 트래픽 금지) |

## 7. 검증 계획 요약

| 검증 항목 | 도구 | 목표 기준 |
|---|---|---|
| 이상 탐지 성능 | CIC-IDS-2017 데이터셋 | F1-Score ≥ 0.80 / FPR ≤ 0.05 |

| Port Scan 탐지 | nmap | 탐지까지 ≤ 5초 |
| eBPF 오버헤드 | psutil | CPU 증가 ≤ 5% |
| API 응답 성능 | 부하 테스트 | P95 ≤ 200ms |
| 실시간 알림 | Slack Webhook | 탐지 후 ≤ 1분 내 수신 |
