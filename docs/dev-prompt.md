각 단계가 끝날 때마다 에이전트가 검수 보고를 출력하고 멈춥니다.

## 붙여넣을 프롬프트 (여기서부터 복사) ↓↓↓

너는 eBPF Trace 프로젝트의 개발자다. 이번 작업의 최우선 목표는 **네트워크를 전혀 모르는 처음 사용자도 화면만 보고 상황을 이해하고 조작할 수 있는 UI/UX**를 만드는 것이고, 그다음이 운영 배포다. 아래 규칙과 단계를 따른다.

### 프로젝트 컨텍스트
- 아키텍처: eBPF/XDP 커널 관찰(XDP_PASS 전용, 차단 안 함) → Collector(피처 25개) → FastAPI(PostgreSQL 17/Redis 7) → React 19 대시보드. 차단은 현장 nftables가 하고, 위험 게이트가 저위험 자동 적용/고위험 2인 승인으로 분기하며 커널 TTL이 최종 안전장치.
- 배포: EC2 `203.0.113.10`(웹/API, 마지막 커밋 bde12ed), VM `192.168.64.2`(Collector). 접속: `ssh -i "don forget.pem" ubuntu@203.0.113.10`, `ssh ubuntu@192.168.64.2`.
- 프론트: React 19 + TypeScript + Vite + Recharts + Zustand + lucide-react. 진입은 `frontend/src/Workspace.tsx`, 사건 대응 화면은 `frontend/src/components/OperationsWorkspace.tsx`(58KB), 그 외 컴포넌트는 `frontend/src/components/`. CSS는 `workspace.css`/`operations.css`/`analysis.css`/`benchmark.css`/`features.css`/`styles.css`. e2e는 `frontend/e2e/`.
- 참고 문서: `docs/overview.md`, `docs/operations-guide.md`, `docs/status-and-verification.md`.
- 현재 화면 상태(실측): 사이드바 메뉴 9개(사건 대응/대응 관리/알림 센터/대시보드/탐지 이벤트/탐지 시나리오/시스템 상태/데이터 분석/탐지 설정) + LAB(공급망 안내 시연). 대시보드 요약 카드 4개(저장된 탐지 이벤트, 실시간 패킷 pps, 실시간 대역폭 Mbps, 분석 엔진).

### UX가 지금 어려운 지점 (실측 기반 — 이걸 개선 대상으로 삼는다)
1. 전문 용어가 그대로 노출됨: `pps`, `Mbps`, `Collector`, `Isolation Forest`, `XDP`, `하이브리드`, `SYN_FLOOD`/`PORT_SCAN`/`LARGE_FLOW`/`TRAFFIC_SPIKE`, `Bearer 토큰`, `anomaly_threshold`.
2. 상태 배너가 "무슨 일인지 / 지금 뭘 해야 하는지"를 초보자 언어로 설명하지 않음(예: "Collector 연결 대기").
3. 메뉴가 9개+로 많아 처음 사용자가 어디부터 볼지 모름.
4. 값이 없을 때 `—`만 표시되어 "고장인지 정상인지" 구분이 안 됨.
5. 심각도/탐지 유형이 영어 코드로 표시됨.

### 작업 규칙 (반드시 지킴)
1. **한 번에 한 단계만.** 건너뛰거나 앞당기지 않는다.
2. 단계 시작 전 관련 파일을 실제로 읽고 현재 구현·용어·클래스명을 확인한다. 추측 금지.
3. **기존 기능·데이터·API·테스트를 깨뜨리지 않는다.** 표시 문구와 레이아웃 위주로 바꾸고, 로직 변경이 필요하면 최소 범위로 한다. 전문 용어는 "쉬운 말(원어)" 형태로 병기하거나 툴팁으로 보존한다(감사·발표 대비).
4. 프론트 변경 시 반드시 검증: `cd frontend && npm run build`, 가능하면 `npm run test:e2e`. e2e가 문구 변경으로 깨지면 셀렉터/기대 문구도 함께 고친다.
5. 접근성 유지: `aria-label`, `role`, 대비, 키보드 포커스. 모바일(≤768px) 레이아웃이 깨지지 않게 한다.
6. 비밀값·토큰은 화면·코드·로그에 노출하지 않는다.
7. 커밋은 명시적 요청 시에만. main 직접 푸시 금지. 파괴적 작업은 실행 전 승인 요청.
8. 검증 실행이 불가한 환경이면 "실행 불가"와 원인을 밝히고 추정을 사실로 보고하지 않는다.

### 디자인 원칙 (모든 UX 단계 공통)
- **행동 중심 언어**: "이렇게 하세요"를 버튼·문장으로. 명사 나열 대신 동사로.
- **쉬운 말 + 원어 병기**: 예) "실시간 패킷 수(pps)", "이상 탐지 AI(Isolation Forest)". 툴팁으로 한 줄 설명.
- **상태는 3색 신호등**: 정상(초록)/주의(노랑)/문제(빨강) + 한 줄 원인 + 다음 행동 버튼.
- **빈 값 구분**: 데이터 없음 / 연결 대기 / 오류를 서로 다른 문구·아이콘으로. 그냥 `—` 금지.
- **점진적 노출**: 처음엔 핵심만, 상세는 "자세히 보기"로 접어둠.
- 색·아이콘·용어는 화면 전체에서 일관되게. 기존 `lucide-react` 아이콘과 CSS 토큰을 재사용한다.

### 단계 정의 — Part A: UX 개선 (먼저 진행)

**[단계 0] 착수 점검 + 용어 인벤토리**
- `frontend/src/Workspace.tsx`, `components/OperationsWorkspace.tsx`, `components/*.tsx`, 관련 CSS를 읽는다.
- 화면에 노출되는 **어려운 용어·영어 코드·빈 값 처리**를 전부 목록화하고, 각각 제안할 "쉬운 말(원어 병기)"을 표로 만든다.
- `npm run build`/`npm run test:e2e` 베이스라인 실행(불가하면 원인 보고).
- 완료 근거: 용어 매핑 표 + 검증 베이스라인 확보. **이 단계는 코드를 바꾸지 않는다.**

**[단계 1] 용어를 쉬운 말로 (표시 레이어)**
- 심각도(critical/high/medium/low) → "긴급/높음/보통/낮음", 탐지 유형(SYN_FLOOD 등) → "연결 폭주(SYN Flood)" 식 한글+원어. 지표 라벨에 단위 설명·툴팁 추가.
- 표시 문구만 바꾸고 내부 값/API/enum은 유지. 매핑은 한 곳(예: `frontend/src/labels.ts`)에 모아 재사용.
- 완료 근거: 대시보드·이벤트·시나리오 화면에서 영어 코드가 사용자용 텍스트로 노출되지 않음. build 통과. e2e 문구 기대치 갱신.

**[단계 2] 상태 신호등 + 다음 행동 배너**
- 헬스/연결 배너를 정상(초록)/주의(노랑)/문제(빨강) 3색 + 한 줄 원인 + 다음 행동 버튼(예: "수집기 상태 보기", "다시 시도")으로 재구성. "Collector 연결 대기" → "네트워크 수집기가 아직 연결되지 않았어요. 잠시 기다리거나 [상태 확인]을 눌러 보세요." 식.
- 빈 값 `—`를 "데이터 없음/연결 대기/오류"로 구분 표기(아이콘 포함).
- 완료 근거: 세 가지 상태가 시각적으로 구분되고 각 상태에 다음 행동이 있음. build 통과.

**[단계 3] 첫 화면 온보딩 · 메뉴 그룹화**
- 처음 방문자를 위한 짧은 안내(카드/툴팁/1회 노출 배너): "이 화면은 무엇을 보여주나요 / 무엇부터 눌러보면 되나요". "탐지 시나리오 열기"를 눈에 띄는 1차 행동으로.
- 사이드바 9개 메뉴를 사용자 여정 기준으로 그룹화(예: 보기 / 대응 / 실습·분석 / 설정)하고, 상급 기능은 접어둔다. 라벨을 초보자 언어로 점검.
- 완료 근거: 처음 사용자가 "먼저 볼 화면"과 "먼저 누를 버튼"을 화면만으로 알 수 있음. 기존 라우팅(hash) 유지. build 통과.

**[단계 4] 시나리오·이벤트 흐름을 이야기처럼**
- 탐지 시나리오 실행 화면에서 단계 진행(정상→탐색→폭주→대량 전송→회복)을 진행 표시줄+쉬운 설명으로 보여주고, 결과를 "무엇을 탐지했고 왜 그렇게 판단했는지" 한 문장으로 요약.
- 이벤트 상세의 원시 피처(raw_features)는 "자세히 보기"로 접고, 상단에는 사람이 읽는 요약을 둔다.
- 완료 근거: 시나리오/이벤트를 처음 보는 사람이 결과의 의미를 읽을 수 있음. build·가능 시 e2e 통과.

**[단계 5] 사건 대응 워크스페이스 초보자화 (OperationsWorkspace)**
- 단계별 "다음 할 일" 버튼과 문구를 초보자 언어로. 위험 게이트 점수·근거를 "왜 자동으로 처리했는지/왜 승인이 필요한지"를 쉬운 문장으로. 승인/해제/복구 버튼의 결과를 명확히 피드백.
- 전문 용어(TTL, CIDR, nftables 등)는 툴팁·괄호 설명으로 병기하되 기능은 유지.
- 완료 근거: 승인자·담당자가 아닌 사람도 각 버튼이 무엇을 하는지 이해 가능. build 통과. 기존 2인 승인 로직·API 불변.

**[단계 6] 반응형·접근성·일관성 마감**
- 모바일(≤768px)에서 카드·표·버튼이 깨지지 않게. 색/아이콘/용어 일관성 최종 점검. 색만으로 정보 전달하지 않도록 텍스트·아이콘 병행. 포커스 순서·`aria` 점검.
- 완료 근거: 데스크톱/모바일 build·e2e 통과, overflow 없음, 대비/포커스 확인.

### 단계 정의 — Part B: 운영 배포 (UX 이후, 기존 계획)
**[단계 7] VM Collector v2 갱신** → **[단계 8] EC2 용량 확보·CI/CD 배포 복구** → **[단계 9] Slack/SMTP 실제 알림 검증** → **[단계 10] 독립 ML 검증·LIVE Shadow 7일** → **[단계 11] Terraform 정합(apply는 승인)** → **[단계 12] HTTPS 종단(Caddy)** → **[단계 13] 비기능 실측·통합 재검증·릴리즈**.
(각 세부 완료 근거는 `docs/status-and-verification.md`와 `docs/operations-guide.md`를 따른다. UX 단계가 끝나기 전에는 Part B로 넘어가지 않는다.)

### 시작 지시
지금 **[단계 0] 착수 점검 + 용어 인벤토리**부터 시작하라. 코드를 바꾸지 말고, 용어 매핑 표와 검증 베이스라인을 위 출력 형식으로 보고한 뒤 멈추고 내 지시를 기다려라.

### 사용 방법
1. 위 블록 전체를 복사해 개발 세션에 붙여넣습니다.
2. [단계 0]에서 에이전트가 **용어 매핑 표**(어려운 말 → 쉬운 말)를 먼저 보여주고 멈춥니다. 여기서 원하는 표현을 지정·수정하면 이후 단계에 반영됩니다.
3. 각 단계 검수 보고에 `Before → After` 문구 비교가 포함되므로, 화면을 열지 않고도 변화가 검수됩니다.
4. UX(단계 0~6)를 먼저 끝내고, 운영 배포(단계 7~13)로 넘어갑니다.
5. 특정 단계부터 하려면 마지막 "시작 지시"의 단계 번호만 바꾸세요.
