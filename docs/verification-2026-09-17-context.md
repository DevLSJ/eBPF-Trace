# 전체 요일 PCAP · Context v2 검증

## 결과의 범위

5일 PCAP 52,433,389,872 bytes에서 15,226,375개 피처 구간을 생성하고 12,250,475개(80.46%)를 정답과 매칭했습니다. 25개 피처 지도학습 후보의 시험 F1은 **90.98%**, Precision **84.44%**, Recall **98.62%**, 정상 오탐률 **0.26%**입니다.

**이 점수는 전체 14종 공격의 성능이 아닙니다.** 연결·시간 분리 후 시험에 남은 공격은 FTP-Patator, SSH-Patator, Web Brute Force, Bot 4종입니다. 나머지 10종에는 시험 근거가 없습니다. 같은 공격 실행이 여러 시간 블록에 걸칠 수 있고 목·금요일 자료는 이전 개발에서도 사용했습니다. 신규 공격 실행·별도 환경 검증이 필요하며, 실험 모델은 운영 승인하지 않았습니다.

근거: [준비 상태](../ml/reports/evaluation/preparation.json), [실험 보고서](../ml/reports/evaluation/context-v2.json). 원본·피처·결합 결과 해시와 소프트웨어 버전을 기록했습니다. 원본 패킷이나 공격을 네트워크에 재전송하지 않았습니다.

## 피처와 처리 개선

- 기존 9개에 목적지·서비스별 PPS/bytes/SYN·10초 출발지 수, 역방향 PPS/bytes, 양방향 PPS/bytes/SYN 비율, 역방향 패킷 비율, 출발지·목적지 10초 PPS를 추가했습니다.
- 오프라인과 실시간 Collector가 같은 계산기를 사용합니다. 실제 커널/스레드 스케줄링과 오프라인 100ms snapshot·1초 flush의 차이는 남습니다.
- 흐름별 윈도우는 증분 합계를 유지하고 각 문맥 테이블은 최대 65,536개로 제한합니다. 재생기는 매 패킷의 불변 객체 재생성을 줄였습니다. 이번 실행은 비교 통제된 속도 벤치마크가 아니므로 속도 향상 비율을 주장하지 않습니다.
- 원본·라벨·코드·출력 해시 기반 재개로 피처 계산이 그대로인 경우 정답 결합만 갱신합니다. CPU/메모리를 고려해 준비 작업자는 1~2개로 제한합니다.
- 구버전 입력의 미관측 문맥은 `null`입니다. 스키마 2는 25개 모두 필요하며 누락 입력은 거부합니다. 역방향 부재를 연결 실패로 해석하지 않습니다.
- 새 문맥은 기존 이벤트 JSON에 저장되고 이벤트 상세에서 확인됩니다. 서비스 단위 SYN 집계는 여러 작은 출발지의 합산 폭주도 기존 임계값으로 검사합니다.

## 학습·보정·시험

프로토콜을 데이터 준비 전에 저장했습니다. 5분 시간 블록과 방향을 정규화한 연결 tuple을 각각 60/20/20 슬롯에 배정하고 배정이 일치한 구간만 남깁니다. 시간 블록 시작 30초와 이전 블록에서 시작한 장기 흐름을 제외합니다. IP·포트·시간은 모델 입력에 포함하지 않습니다.

| 구분 | 구간 수 |
|---|---:|
| 매칭된 입력 | 12,250,475 |
| 시간 경계·장기 흐름 제외 | 2,966,124 |
| 연결·시간 배정 불일치 제외 | 5,269,324 |
| 실제 학습 표본 | 358,023 |
| 임계값 보정 표본 | 405,358 |

정상 학습 최대 20만, 공격 유형별 최대 3만을 무작위 우선순위 reservoir로 보관합니다. IF는 정상만 학습합니다. HGB는 이진 정상/공격 지도학습과 균형 가중치를 사용합니다. 보정·시험은 분리 조건에 남은 전체 구간을 평가합니다. 대량 제외와 낮은 공격 비중 때문에 전체 캡처를 대표하는 점수로 해석하면 안 됩니다.

임계값은 보정 FPR ≤ 5% 조건에서 F1을 최대화합니다. 후보 선택도 보정 데이터로만 수행하며 `selection.json`을 시험 점수 산출 전에 저장합니다. 시험 성능을 확인한 뒤 설정이나 임계값을 변경하지 않았습니다. 최초 평가 후 공격 유형 범위 필드만 추가해 같은 설정으로 재생성했습니다.

| 모델 | 보정 F1 | 시험 F1 | 시험 Recall | 시험 FPR |

기본 IF 6/9/25개는 100트리·256표본으로 비교합니다. 확장 IF는 128트리·1,024표본, HGB는 120회 반복·31 leaf·최소 leaf 30·L2 1이며 early stopping을 사용하지 않습니다. seed는 42입니다. [이전 F1 62.92%](verification-2026-09-17-upgrade.md)는 표본과 분리 기준이 다릅니다.

## 다음 검증에 필요한 데이터

새로운 실행에서 정상 업무·백업·대량 전송과 공격을 별도로 수집하고, 센서 위치·타임존·NAT 매핑·공격 시작/종료 시각을 남겨야 합니다. 이번 시험에 없는 10종 및 Bot을 포함해 학습과 다른 실행을 최종 검증에 사용합니다. 공격 유형마다 새로운 실행·피해 호스트·정상 대조군을 확보하고 목표 F1과 FPR을 함께 확인합니다. 이 자료가 있어야 개발 데이터의 수치를 운영 적용 근거로 바꿀 수 있습니다.

알림·사건 대응의 후속 설계는 [운영 대응 기획](response-design-2026-09-17.md)에 있습니다. 이번 변경은 Slack/Gmail 발송이나 자동 차단을 활성화하지 않습니다.

## 코드 검증

로컬에서 실제 PostgreSQL·Redis를 포함한 68개 테스트가 통과했고, 준비 완료 후 캡처 보고서 테스트와 변경된 연결 상태 테스트를 추가 확인했습니다. GitHub CI에서는 전체 **69개 Python 테스트**, **16개 데스크톱·모바일 브라우저 테스트**, Ruff·TypeScript·Vite·eBPF 컴파일이 통과했습니다. 빌드된 백엔드 이미지 안에서 앱·공유 피처 계약 import도 확인했습니다.

## 배포와 운영 화면

코드 `bde12ed902b37ba9f818e44ea1e816ccd004e0dd`를 main에 푸시했습니다. [CI 실행](https://github.com/DevLSJ/eBPF-Trace/actions/runs/35198162568)의 테스트·이미지 빌드·EC2 웹/API 배포는 성공했습니다. EC2의 `/home/ubuntu/ebpf-current`도 이 릴리즈를 가리킵니다.

마지막 VM Collector 갱신은 runner의 `sudo -n systemctl stop ebpf-collector.service` 실패로 보류됐습니다. 기존 Collector는 계속 연결돼 있으며 2026-09-17 08:16 UTC 화면 캡처의 관측 스키마는 **1**입니다. 준비된 v2 코드를 현재 수집기가 실행하고 있다고 해석하면 안 됩니다. VM 관리자의 시작·중지 권한 설정 후 해당 배포 job을 재실행해야 합니다. [설정 방법](operations.md#vm-수집기)

두 번째 배포 시도는 새 이미지 설치 후 남은 디스크 공간 787 MiB가 최소 기준 900 MiB보다 작아 사전 검사에서 중단됐습니다. 현재/직전 이미지와 DB·볼륨을 보존하고, 사용 중이지 않은 가장 오래된 `2eae69b` 이미지 두 개를 정리해 약 1.2 GiB를 확보했습니다. 운영 데이터는 삭제하지 않았습니다.

운영 API를 사용한 [스크린샷 manifest](screenshots/capture-manifest.json)에 캡처 시각·Collector 상태·5일 매칭·모델 지표를 기록했습니다. 화면 10개에서 page error 0, 데스크톱·모바일·모델 비교 화면 overflow false를 확인했습니다. 시나리오 화면은 명시적으로 표시된 기존 모의 실행을 조회했으며 새 공격이나 외부 알림을 전송하지 않았습니다.
